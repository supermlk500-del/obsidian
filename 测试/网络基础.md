## 通信方式

### 1. 单工（Simplex）

- **定义**：数据只能单向传输
    
- **特点**：一方发送，另一方只能接收
    
- **示例**：广播、电台
    

### 2. 半双工（Half Duplex）

- **定义**：数据可以双向传输，但**同一时间只能一个方向**
    
- **示例**：对讲机
    

### 3. 全双工（Full Duplex）

- **定义**：数据可同时双向传输
    
- **示例**：电话、以太网通信

## OSI 七层模型（重点）

![[OSI七层模型以及作用.png]]

> **口诀（自下而上）**：物数网传会表应

### 1️⃣ 物理层（Physical）

- 负责比特流的传输（0/1）
    
- 关注：电压、接口、网线
    

### 2️⃣ 数据链路层（Data Link）

- 负责帧传输、MAC 地址
    
- 常见协议：Ethernet
    

### 3️⃣ 网络层（Network）

- 负责 **IP 地址**、路由选择
    
- 核心协议：IP、ICMP
    

### 4️⃣ 传输层（Transport）

- 建立端到端连接
    
- 核心协议：TCP、UDP
    

### 5️⃣ 会话层（Session）

- 建立、管理、终止会话
    

### 6️⃣ 表示层（Presentation）

- 数据编码、加密、解密、压缩
    

### 7️⃣ 应用层（Application）

- 提供用户访问接口
    
- 常见协议：HTTP、HTTPS、FTP

## TCP / UDP / HTTP/HTTPS

### 1. TCP（Transmission Control Protocol）

- 面向连接
    
- 可靠传输
    
- 有序、不丢包
    
- 应用：HTTP、HTTPS
    

### 2. UDP（User Datagram Protocol）

- 无连接
    
- 不保证可靠性
    
- 速度快
    
- 应用：视频直播、语音通话
    

### 3. HTTP

- 基于 TCP 的应用层协议
    
- 无状态
    
- 用于浏览器与 Web 服务器通信


- HTTP是HyperTextTransferProtocol（超文本传输协议）的简写，
它是TCP/IP协议的一个应用层协议，用于定义WEB浏览器与WEB服务
器之间交换数据的过程。
- **HTTP协议的版本**：1.0、1.1（主流）、2.0
	- 在HTTP1.0协议中，客户端与web服务器建立连接后（建立一个TCP）只能发起一个HTTP请求获得一个web资源（短链接）。
	- HTTP1.1协议，客户端与web服务器建立连接后（TCP链接）：在一个TCP连接上可以发起多个http请求获取多个web资源（长链接）。

- **客户端连上web服务器后，若想获得web服务器中的某个web资源，
需遵守一定的通讯格式
- **表示要通过HTTP协议来定位网络资源
- **先建立TCP连接，后发数据
- **基于TCP连接的传输协议Http请求的默认端口是80基于请求一响应模式的协议
**

### HTTPS
**HTTPS（Hyper Text Transfer Protocol over Secure Socket Layer）**  
即：**安全版的 HTTP 协议**。

- HTTPS 是以**安全为目标的 HTTP 通道**
    
- 本质：**HTTP + SSL/TLS**
    
- 在 **HTTP 和 TCP 之间增加了一层 SSL/TLS 加密层**
    

📌 简化理解：

> **HTTPS = HTTP + 加密 + 身份认证 + 数据完整性校验**

#### HTTP 的问题（缺陷）

HTTP 协议的特点：

- 明文传输
    
- 不加密
    
- 不验证通信双方身份
    
- 不保证数据完整性
    

🚨 风险：

- 数据容易被**窃听**
    
- 数据可能被**篡改**
    
- 无法确认访问的是不是真实服务器
    

📍 不适合传输：

- 密码
    
- 身份证信息
    
- 银行卡号
    
- 支付信息


#### 1️⃣ SSL（Secure Sockets Layer）

- 安全套接字层
    
- 为网络通信提供：
    
    - **加密**
        
    - **身份认证**
        
    - **数据完整性保护**
        

⚠️ 说明：

- **SSL 已逐渐被 TLS 取代**
    
- 但实际使用中仍习惯统称为 **SSL**
    

#### 2️⃣ TLS（Transport Layer Security）

- SSL 的升级版本
    
- 更安全
    
- 目前主流使用的是 **TLS 1.2 / TLS 1.3**
    

📌 实际上：

> **HTTPS = HTTP + TLS**

#### 主要解决安全方向问题

| 安全目标  | 说明      |
| ----- | ------- |
| 加密传输  | 防止数据被窃听 |
| 身份认证  | 确认服务器身份 |
| 数据完整性 | 防止数据被篡改 |

## Ping 与 ICMP（结合抓包理解）

### 1. Ping 的本质

- 使用 **ICMP 协议**
    
- 用于检测网络是否可达
    

### 2. Wireshark 抓包分析

- Protocol：ICMP
    
- 请求包：Echo (ping) request
    
- 响应包：Echo (ping) reply
    
- Source / Destination：
    
    - 本机 IP（如：192.168.220.236）
        
    - 目标 IP（如：36.152.44.93）
        

📌 说明：

- `192.168.x.x` → 内网 IP
    
- 公网 IP → 外部服务器
    

---

- “从浏览器访问网页时，首先通过 **DNS 解析**将域名转换为 IP 地址；随后浏览器与该 IP 指向的服务器建立 **TCP 连接（及 SSL/TLS 握手）**；最后浏览器发送 HTTP 请求，资源服务器处理后将结果响应给客户端。”

## 三次握手（TCP 建立连接）

1️⃣ 客户端 → 服务器：SYN  
2️⃣ 服务器 → 客户端：SYN + ACK  
3️⃣ 客户端 → 服务器：ACK

📌 目的：

- 确认双方收发能力正常
    

---

## 四次挥手（TCP 断开连接）

1️⃣ 客户端：FIN  
2️⃣ 服务器：ACK  
3️⃣ 服务器：FIN  
4️⃣ 客户端：ACK

📌 原因：

- TCP 是全双工，需要分别关闭

### cookie、session、token的区别

####  核心概念：它们到底是什么？

- **Cookie**：服务器发给浏览器的一张“小纸条”，由浏览器存储，下次请求自动带上。
    
- **Session**：服务器端的“客户档案库”，通过 `SessionID` 与 Cookie 绑定来识别用户。
    
- **Token (JWT)**：服务器签发的“电子身份证”，自带防伪签名和用户信息，客户端需手动携带。
    

---

#### 深度对比矩阵

| **维度**   | **Cookie**    | **Session**       | **Token (JWT)**      |
| -------- | ------------- | ----------------- | -------------------- |
| **存储位置** | 客户端（浏览器）      | 服务器（内存/Redis/DB）  | 客户端（LocalStorage/内存） |
| **数据性质** | 键值对（明文）       | 敏感对象（加密存在后端）      | 编码后的 JSON（自带签名）      |
| **大小限制** | **4KB**（含属性）  | 理论无限制（取决于内存）      | 理论无限制（建议 < 8KB）      |
| **生命周期** | 可选：关浏览器消失或持久化 | 依赖 SessionID 生命周期 | 令牌内部硬编码，到期失效         |
| **主要优点** | 简单、浏览器自动管理    | 安全性高、支持主动注销       | **无状态**、跨域友好、高并发     |
| **主要缺点** | 容易被拦截、大小受限    | 占用服务器资源、集群同步难     | 签发后服务器难以中途作废         |

---

####  生命周期与注销机制

1. **Cookie 生命周期**：
    
    - **会话型**：不设 `Expires`，浏览器关闭即焚。
        
    - **持久型**：设置 `Max-Age`，存在硬盘中，到期前一直有效。
        
2. **Session 生命周期**：
    
    - **双重校验**：不仅要求客户端 `SessionID` 有效，还要求后端 Redis/内存中的数据未过期。
        
    - **强制下线**：服务器端直接删除记录，用户即刻失效。
        
3. **Token 生命周期**：
    
    - **刚性过期**：JWT 内部包含 `exp` 字段。一旦签发，除非到期，否则无法撤回（除非配合黑名单）。
        
    - **续航方案**：常用 `Access Token`（短效）+ `Refresh Token`（长效）的组合。
        

---

####  安全性最佳实践（防坑指南）

- **防 XSS 攻击**：Cookie 必须设置 `HttpOnly: true`，防止 JS 读取敏感信息。
    
- **防 CSRF 攻击**：Session 容易被伪造请求。Token 方案天然防 CSRF，因为请求头 `Authorization` 无法被自动伪造。
    
- **敏感信息**：**千万不要**在 JWT 的 Payload 中存密码、手机号等私密数据，它只是 Base64 编码，等同于明文。
    
- **存储选择**：
    
    - 需主动控制登录状态（如踢人） $\rightarrow$ **Session**。
        
    - 需跨域名、高性能、微服务 $\rightarrow$ **Token**。
        

---

####  简单流程总结

1. **Session 模式**：浏览器拿 `ID` $\rightarrow$ 后端查库 $\rightarrow$ 确认身份（**查表法**）。
    
2. **Token 模式**：客户端拿 `密文` $\rightarrow$ 后端解密签名 $\rightarrow$ 确认有效（**计算法**）。
