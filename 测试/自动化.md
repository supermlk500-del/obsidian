# 自动化测试学习路线与 SaaaTest 框架

> 当前学习目标：使用 Python + pytest + requests，独立搭建织慧通 SaaS 项目的接口自动化框架。
>
> 学习方式：先把一个接口写通，再拆分到现有文件夹；先完成主流程，再扩展异常场景、数据库和性能测试。

---

## 一、先明确我们要解决什么问题

自动化测试不是把所有接口简单调用一遍，而是要回答三个问题：

1. 请求是否发对了？
2. 返回结果是否符合预期？
3. 多个接口之间的数据能不能正确传递？

当前主流程是：

```text
准备测试账号
    ↓
登录，获取 token
    ↓
查询批次，获取 batchId
    ↓
查询启用的工艺路线，获取 routeId
    ↓
创建订单，获取 orderId
    ↓
创建订单明细，获取 orderItemId
    ↓
给订单明细绑定批次
    ↓
创建生产计划，获取 planId
    ↓
查询甘特图
```

注意：当前 SaaS 后端没有公开的普通用户注册接口。`/system/user` 是管理员创建系统用户接口，所以第一版主流程从“准备好的测试账号登录”开始，不把注册接口凭空写进框架。

## 二、SaaaTest 当前框架

当前项目目录：

```text
SaaaTest/
├── config/
│   └── config.py
├── data/
│   └── login.yaml
├── utils/
│   └── read_file.py
├── core/
│   └── http_client.py
├── apis/
│   └── auth_api.py
├── test_cases/
│   └── test_01_login.py
├── conftest.py
├── pytest.ini
├── requirements.txt
└── login.py
```

文件夹分工只按当前项目划分，不额外增加复杂层级。

### 1. `config/`：项目配置

保存服务地址、公共请求头和超时时间。

```python
BASE_URL = "http://127.0.0.1:8080"

DEFAULT_HEADERS = {
    "Accept": "application/json",
    "Content-Type": "application/json",
}
```

它只提供配置，不发送请求，也不做断言。

### 2. `data/`：测试数据

保存测试输入和预期结果，例如用户名、密码、预期状态码和提示信息。

```yaml
login_data:
  - name: login_success
    username: admin
    password: admin123
    expect_http_code: 200
    expect_code: 200
    expect_msg: success
```

即使现在只有一组数据，也保留列表结构。以后增加第二组登录数据时，只添加第二个 `-`，测试代码不需要改变。

### 3. `utils/`：通用工具

保存与业务无关的通用方法，例如：

- 读取 YAML、JSON、CSV；
- 生成随机订单号；
- 获取项目路径；
- 日志处理。

例如 `utils/read_file.py` 只负责读取文件，不知道文件里是登录数据还是订单数据。

### 4. `core/`：公共请求能力

`core/http_client.py` 负责：

- 使用 `requests.Session`；
- 拼接完整 URL；
- 统一公共请求头；
- 支持 GET、POST、PUT、PATCH、DELETE；
- 统一超时时间。

它不负责登录、订单和甘特图等业务，也不写业务断言。

### 5. `apis/`：业务接口封装

每个业务模块放在 `apis/` 中：

```text
apis/auth_api.py
apis/batch_api.py
apis/process_route_api.py
apis/order_api.py
apis/plan_api.py
```

每个方法对应一个后端接口，例如：

```text
AuthApi.login()
BatchApi.resource_pool()
ProcessRouteApi.list_active()
OrderApi.create_order()
OrderApi.create_item()
OrderApi.create_batch_link()
ProductionPlanApi.create()
ProductionPlanApi.gantt()
```

接口层负责接口路径、请求方式和请求参数，但不负责最终测试断言。

### 6. `test_cases/`：测试和业务流程

这里负责：

- 读取测试数据；
- pytest 参数化；
- 调用接口对象；
- 串联多个接口；
- 提取并传递业务 ID；
- 编写断言。

当前登录测试放在：

```text
test_cases/test_01_login.py
```

主流程将来放在：

```text
test_cases/test_02_order_to_gantt.py
```

暂时不单独创建 `workflow/` 文件夹，因为当前项目还没有复杂到需要再拆一层。

### 7. `conftest.py`：公共前置和后置

后续用于保存：

- 登录 Fixture；
- 测试前准备基础数据；
- 测试后清理订单和生产计划；
- 公共测试环境处理。

文件名必须是 `conftest.py`，不能写成 `conftests.py`，否则 pytest 不会自动识别。

### 8. `login.py`：实验脚本

`login.py` 是最初用来验证接口的单文件脚本，可以保留作为学习记录，但它不是正式测试入口。

正式测试应该从 `test_cases/` 中运行：

```bash
pytest -vs
```

## 三、一个登录接口是怎么流转的

登录测试的完整调用链：

```text
data/login.yaml
    ↓
utils/read_file.py 读取 YAML
    ↓
test_cases/test_01_login.py 参数化并断言
    ↓
apis/auth_api.py 组装登录请求
    ↓
core/http_client.py 发送 HTTP 请求
    ↓
config/config.py 提供 BASE_URL 和公共请求头
    ↓
后端 /auth/login
```

每一层只做自己的事情：

```text
config：地址是什么
data：用什么数据测试
utils：怎么读取数据
core：怎么发送请求
apis：调用哪个业务接口
test_cases：怎么验证结果、怎么串联流程
```

## 四、登录数据参数化

### 1. `case` 是什么

`case` 不是 pytest 的固定关键字，只是测试函数接收一组数据时使用的变量名。

```python
login_cases = read_yaml("login.yaml")["login_data"]
```

读取后：

```python
login_cases = [
    {
        "name": "login_success",
        "username": "admin",
        "password": "admin123",
        "expect_http_code": 200,
        "expect_code": 200,
        "expect_msg": "success",
    }
]
```

pytest 参数化：

```python
@pytest.mark.parametrize(
    "case",
    login_cases,
    ids=[case["name"] for case in login_cases],
)
def test_login(case):
    ...
```

列表中有几组数据，测试就执行几次。现在列表中只有一组数据，所以只执行一次。

### 2. 当前登录测试的职责

登录测试只负责调用登录接口并验证：

```python
response.status_code == 200
result["code"] == 200
result["msg"] == "success"
result["data"]["token"] 存在
```

不要在 `data/login.yaml` 中写请求代码，也不要在 `apis/auth_api.py` 中写 `assert`。

## 五、HTTP 请求和响应的基本规则

### 1. 请求方式

公共请求层使用一个通用方法：

```python
request(method, path, ...)
```

这样可以支持：

```python
client.request("GET", "/auth/me")
client.request("POST", "/api/orders", json=data)
client.request("PUT", "/api/orders/1", json=data)
client.request("DELETE", "/api/orders/1")
```

### 2. `json`、`data` 和 `params`

| 用法 | 作用 | 典型场景 |
|---|---|---|
| `json=data` | 发送 JSON 请求体 | 登录、创建订单、创建计划 |
| `data=data` | 发送表单数据 | 表单接口 |
| `params=data` | 拼接 URL 查询参数 | 分页查询、条件查询 |
| `files=files` | 上传文件 | 质检图片、附件 |

### 3. 织慧通响应结构

普通接口：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

分页接口：

```json
{
  "code": 200,
  "msg": "success",
  "rows": [],
  "total": 0
}
```

不要把分页数据写成 `data.rows`，它实际位于 `rows`。

测试时通常同时验证：

```text
HTTP status_code：网络层是否成功
JSON code：业务层是否成功
业务字段：token、orderId、planId、tasks 是否存在
```

## 六、织慧通主流程接口清单

| 顺序 | 接口 | 需要提取的数据 |
|---|---|---|
| 1 | `POST /auth/login` | `data.token` |
| 2 | `GET /auth/me` | 校验当前用户和权限 |
| 3 | `GET /api/batches/resource-pool` | `rows[0].batchId` |
| 4 | `GET /api/process-routes?isActive=1` | `rows[0].routeId` |
| 5 | `POST /api/orders` | `data.orderId` |
| 6 | `POST /api/orders/{orderId}/items` | `data.orderItemId` |
| 7 | `POST /api/orders/{orderId}/batches` | 创建绑定关系 |
| 8 | `POST /api/production-plans` | `data.planId` |
| 9 | `GET /api/production-plans/{planId}/gantt` | `data.tasks` |

所有登录后的接口都需要：

```http
Authorization: Bearer <token>
```

## 七、主流程中的数据传递

主流程不能把 ID 写死，也不能依赖上一个测试文件先执行。数据应该在同一个流程测试中按顺序传递：

```text
token
  ↓
所有登录后接口的 Authorization

batchId + routeId
  ↓
创建生产计划的请求体

orderId
  ↓
创建订单明细、绑定批次

orderItemId
  ↓
绑定批次、创建生产计划

planId
  ↓
查询甘特图
```

第一版建议在内存变量中传递：

```python
token = ...
order_id = ...
order_item_id = ...
plan_id = ...
```

不要像旧项目一样把 token 写入 YAML 文件作为跨用例共享状态。文件状态容易被覆盖，也容易产生执行顺序依赖。

## 八、主流程的实现顺序

不要一次写完全部接口，按下面顺序推进。

### 第 1 步：登录

完成：

- `AuthApi.login()`；
- 登录数据 YAML；
- 登录成功断言；
- 提取 token。

### 第 2 步：当前用户

增加：

```text
AuthApi.me(token)
```

验证 token 确实能够访问受保护接口。

### 第 3 步：查询基础数据

增加：

```text
BatchApi.resource_pool(token)
ProcessRouteApi.list_active(token)
```

验证能拿到可用的 `batchId` 和 `routeId`。

### 第 4 步：创建订单链

依次增加：

```text
OrderApi.create_order()
OrderApi.create_item()
OrderApi.create_batch_link()
```

每一步都要提取并断言 ID 存在。

### 第 5 步：创建计划和甘特图

增加：

```text
ProductionPlanApi.create()
ProductionPlanApi.gantt()
```

最终断言：

```text
planId 存在
HTTP 状态码为 200
业务 code 为 200
data.tasks 存在
```

## 九、主流程的真实前置条件

创建生产计划之前，后端会检查：

- 订单存在；
- 订单明细属于该订单；
- 批次已经绑定到订单明细；
- 工艺路线处于启用状态；
- 工艺路线至少有一个工序；
- 批次宽度和重量满足订单明细要求；
- 登录账号具有对应权限。

所以如果创建计划失败，不要第一时间怀疑 Python 代码，先检查：

```text
token 是否有效
账号是否有权限
batchId 是否真实存在
routeId 是否启用
路线是否配置了工序
orderItemId 是否属于 orderId
批次是否已经绑定
```

## 十、数据清理原则

主流程会创建订单、订单明细、批次绑定和生产计划，因此必须考虑清理。

第一版先保证流程能够跑通，清理可以放到后续 `conftest.py` 中。

理想清理顺序：

```text
取消生产计划
    ↓
删除订单
    ↓
后端级联清理订单明细和批次绑定
```

不要删除测试环境中原有的批次和工艺路线。它们是基础数据，只读取，不删除。

为了保持学习主线清晰，当前暂时不做：

## 十二、常见错误

### 1. YAML 列表格式错误

错误：

```yaml
-name: login_success
```

正确：

```yaml
- name: login_success
```

`-` 后面必须有空格。

### 2. 路径获取错误

```python
Path(__file__).resolve().parents[1]
```

使用 `parents[1]`，不要写成 `parent[1]`。

### 3. 参数化顺序错误

正确：

```python
@pytest.mark.parametrize("case", login_cases)
```

第一个参数是参数名，第二个参数是数据列表。

### 4. Response 和字典混用

如果 API 层返回 `requests.Response`：

```python
result = response.json()
assert result["code"] == 200
```

如果 API 层已经返回 `response.json()` 的字典：

```python
assert result["code"] == 200
```

两种方式选一种，不能重复调用 `.json()`。

### 5. 把断言写进 API 层

API 层应该返回响应：

```python
return response
```

断言统一写在 `test_cases/`。

### 6. 把 token 写死或写入共享文件

token 应该从登录响应中提取，并在当前测试流程中传递：

```python
token = login_result["data"]["token"]
```

不要依赖某个测试文件先运行，也不要让多个测试同时覆盖同一个 token 文件。

## 十三、每完成一个阶段的验收标准

### 登录阶段

- 能读取 `data/login.yaml`；
- 能执行参数化测试；
- 登录成功；
- 能提取 token。

### 基础数据阶段

- 能访问 `/auth/me`；
- 能拿到 `batchId`；
- 能拿到 `routeId`。

### 订单阶段

- 能创建唯一订单；
- 能拿到 `orderId`；
- 能创建订单明细；
- 能拿到 `orderItemId`；
- 能成功绑定批次。

### 排产阶段

- 能创建生产计划；
- 能拿到 `planId`；
- 能查询甘特图；
- `tasks` 中至少有一条工序数据。

### 最终目标

```text
pytest -vs
```

能够稳定执行：

```text
登录 → 查询基础数据 → 创建订单 → 创建明细 → 绑定批次 → 创建计划 → 查询甘特图
```

并且每次执行使用唯一订单号，测试结束后不会污染测试环境。
